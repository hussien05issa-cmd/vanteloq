## Moneris runtime follow-up

The Worker error was reproduced with a bundled adapter and native workerd fetch. Both token exchange and payment loading failed before reaching the fake provider. The adapter now uses `redirect: "manual"`, cancels every non-success response body and rejects it with safe provider-specific errors. Credentials are never forwarded to a redirect target.

Validation: **43 tests passed**, comprising `tests/moneris.test.ts`, `tests/moneris-sync.test.ts` and new `tests/moneris-worker-runtime.test.mjs`. The native Worker checks cover successful token/payment requests and HTTP 300, 301, 302, 303, 304, 307, 308, 399, 401, 429 and 500 responses. Existing tests cover merchant isolation, currency evidence, changed facts, frozen pagination, overnight continuation and database failure recovery. All requests used intercepted fake services, encrypted fictional credentials and disposable local databases. No Moneris production call was made; reporting remains blocked. Publication is not established by these local results.

## Stripe staging follow-up

Correction to the initial audit: the database uniqueness key includes `source_payload_hash`, so a pending, paid or failed payout becomes a distinct immutable evidence version. The old state is intentionally retained as history; it is not the sole surviving state. No production consumer currently reads or sums this staging table. Replacing these rows would discard evidence, so versioning remains unchanged. A future current-state/reporting view must explicitly choose a reviewed version for each external record and must keep payouts separate from revenue.

A focused test did prove a freshness defect: normalization warnings preserved the import cursor but still advanced `lastSuccessfulSyncAt`. The importer now retains the prior successful time while any row requires retry. This keeps the connection's freshness claim consistent with its incomplete import.

Exploratory concurrency limitation: if another operation invalidates the lease while provider requests are in flight, the current importer can append staging evidence before its final lease renewal rejects the run. It cannot publish or promote that run, but a stricter write-time lease fence is future hardening. This was not changed in the bounded freshness fix.

Validation: **11 tests passed** across `tests/stripe-staging-refresh.test.ts` and `tests/stripe.test.ts`. Coverage includes pending-to-paid-to-failed immutable versions, identical retries, signed refund amounts, external-ID isolation across organizations/connections, normalization warning retry with truthful freshness, failed-request cursor preservation and lease release, OAuth grant constraints and signed webhook rejection. All provider traffic was fictional and intercepted; no billing, production records, rollout gate, schema or ledger promotion was changed.
